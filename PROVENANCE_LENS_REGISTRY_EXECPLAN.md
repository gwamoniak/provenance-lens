## Purpose / Big Picture

Layers 1–2 die together under one common attack: strip the metadata, re-encode the pixels. C2PA manifests vanish on upload; the calibration tables in `docs/CALIBRATION.md` measured the SD watermark dropping to 0% detection after a single JPEG re-encode. The registry is the layer built for exactly that world: a generator (or any registrant) records "I produced an asset with this perceptual fingerprint" in a public, append-only log AT CREATION TIME; later, anyone holding a stripped, re-encoded, cropped copy computes the same kind of fingerprint locally and asks the log. After this plan is fully executed, `lens verify screenshot.jpg` on a metadata-stripped copy of a registered asset reports **Indicated** with the finding "matches an asset registered as AI-generated by <registrant> on <date> (verified inclusion proof, Hamming distance <d>)" — and, exactly as important, an unregistered asset reports nothing new, because a miss in a sparse registry means nothing and the wording never implies otherwise.

## Decision Log

- Decision: Perceptual hash is **PDQ** (Meta's open 256-bit standard from the ThreatExchange release; public spec and reference implementation), not pHash. Match = Hamming distance between 256-bit vectors at a threshold MEASURED on our corpora before any verdict influence; the conventional PDQ operating point (distance ≤ 31) is the starting candidate, not a commitment — `docs/CALIBRATION.md` gets a PDQ section with false-match rates at several thresholds over the DIV2K corpus and the W2 transformation battery, and the shipped threshold is chosen from that table.
  Rationale: PDQ is the industry lingua franca for exactly this job (274 lines of public spec, fixed preprocessing, designed for Hamming indexing at scale); an open spec satisfies the same revised-M5 instinct that governed the watermark layer — no black boxes in evidence paths. The threshold-is-the-FPR rule comes from the provenance-registry skill and is non-negotiable.
  Date/Author: 2026-08-02 / agent (plan authoring).
- Decision: The log is an **RFC 6962-style append-only Merkle tree** (the Certificate Transparency / Sigstore-Rekor construction): leaves are registration entries, the operator publishes signed checkpoints (tree size + root hash + signature), and clients verify inclusion proofs and checkpoint consistency LOCALLY. The near-match problem is split honestly: the server maintains an UNTRUSTED Hamming index (multi-index hashing over PDQ words) that merely nominates candidate entries; the client receives candidates WITH inclusion proofs, verifies the proofs, and computes the Hamming distances itself. The server can hide entries (that is detectable by log auditing and yields at worst a false miss — the safe direction); it cannot fabricate a match the client would accept.
  Rationale: membership proofs come from the log; nearness is client-side arithmetic over proof-verified data. Nothing in the trust path depends on the server being honest, which is the only acceptable shape for evidence this project reports.
  Date/Author: 2026-08-02 / agent (plan authoring).
- Decision: Registration entries are `(pdq_hash: [u8; 32], registrant_id, declared_source_type, created_at, registrant_signature over the preceding fields)`, with per-registrant Ed25519 keys registered out of band. A registry hit is vouching, not cryptography over the queried bytes: the finding wording MUST name the registrant and date ("registered by X on Y") and stays `Indication` — never `Proof`, which remains Layer 1's alone.
  Rationale: the entry signature makes registrations non-repudiable and attributable, but a perceptual near-match to a signed entry proves only that someone registered a similar-looking asset. Evidentiary typing (wedge plan) already encodes this ceiling.
  Date/Author: 2026-08-02 / agent (plan authoring).
- Decision: Privacy posture, restated as law for G3: only the PDQ hash ever leaves the device (never bytes, never URLs), only with explicit per-use consent in the UI and a documented always-on statement in the manual; registry endpoints are user-configurable so organizations can point at self-hosted logs; the default build ships with the lookup OFF until the user turns it on. A traffic-shaping refinement (k-anonymity prefix queries: send a hash bucket, receive the bucket's candidates) is recorded as a G3 option, decided there with measured bucket sizes.
  Rationale: the wedge plan's privacy rule ("post-wedge network layers may send perceptual hashes only, with explicit user consent") made this promise before any code existed; the design must keep it structurally, not by policy.
  Date/Author: 2026-08-02 / agent (plan authoring).
- Decision: G2 offers the maintainer two deployment shapes, cost-honest, one to be picked at G0: **G2a, the git-backed pilot** — the log lives as flat files in a public GitHub repository (append-only enforced by CI: every merge re-verifies the Merkle tree extends the previous checkpoint; checkpoints signed in CI with a repo-secret key; clients fetch entries/proofs/checkpoints as static raw files; registrants submit entries by PR). Zero infrastructure cost, self-hostable by forking, and honest about its ceiling (GitHub availability, minutes-scale append latency, and a CI-held signing key — fine for a pilot proving the verification rail, not an institution). **G2b, the service** — a single self-contained Rust binary (SQLite storage, the same Merkle core, HTTP API for submit/lookup/proof/checkpoint), deployable on a ~$5/month VPS; the real path if the pilot earns traffic. The Merkle core and file/wire formats are IDENTICAL in both shapes, so G2a → G2b is a data migration, not a redesign.
  Rationale: the strategic bet (roadmap W4) deserves a rail that can be proven end-to-end without standing infrastructure the project cannot yet justify; the pilot de-risks the design while keeping every trust property (client-side proof verification does not care whether proofs arrive from raw.githubusercontent.com or a daemon).
  Date/Author: 2026-08-02 / agent (plan authoring); maintainer's G0 choice pending.
- Decision: The empty-registry problem is stated, not hidden: at launch the log contains our own test corpus registrations and whatever early registrants volunteer. A sparse registry changes NOTHING about miss semantics (`NoSignal`, and Inconclusive wording already never implies authenticity), and the layer's value at pilot stage is proving the rail — hash, nomination, proof, verdict — not coverage. Outreach to generators is maintainer territory, out of this plan's scope.
  Rationale: the founding rule ("no data ≠ authentic") is precisely what makes an initially-empty registry shippable without dishonesty; pretending otherwise would be the overclaiming this project refuses.
  Date/Author: 2026-08-02 / agent (plan authoring).

## Context and Orientation

The repository (`D:\sandbox\projects\provenance-lens`, public at https://github.com/gwamoniak/provenance-lens) is a Rust workspace: `crates/provenance-core` (sans-IO verification pipeline — it never opens files or sockets; callers inject bytes and transports), `crates/provenance-cli` (the `lens` binary), `crates/provenance-wasm` (WASM wrapper for the browser extension in `extension/`). Four layers produce findings that combine into one of four verdicts (Tampered > Verified > Indicated > Inconclusive); only Layer 1 (C2PA cryptographic validation) may return `Proof`; Layer 3 — this plan — is the stub in `crates/provenance-core/src/layers/registry.rs`, currently returning `NotEvaluated { reason: "gated: no transparency-log registry deployed yet" }`, which is exactly what it must keep saying until G3 completes.

Terms, in plain language. A **perceptual hash** is a small fingerprint computed from what an image LOOKS like (downscaled luminance structure), so re-encoding, mild resizing, or recompression yields a nearby fingerprint where a cryptographic hash would change completely; **PDQ** is Meta's openly specified 256-bit perceptual hash, compared by **Hamming distance** (how many of the 256 bits differ). A **transparency log** is an append-only public record built as a **Merkle tree**: every entry is a leaf, each tree state is summarized by a single root hash, and the operator periodically publishes a signed **checkpoint** (tree size + root hash + signature). An **inclusion proof** is the short chain of hashes that lets a client verify "this entry is under that root" with local arithmetic; a **consistency proof** verifies a newer checkpoint's tree still begins with the older one's (history was appended to, never rewritten). This is the Certificate Transparency construction (RFC 6962), reused by Sigstore's Rekor; we adopt it rather than invent one. **Anchoring** means additionally publishing checkpoint hashes to a public blockchain as outside witnesses — in this project always optional, default off, never on any verdict path (standing wedge-plan decision).

Prior design knowledge lives in `.claude/skills/provenance-registry/SKILL.md` (hashing rules, log model, privacy, failure semantics — this plan supersedes none of it, it operationalizes it) and the origin proposal `ai-content-verifier-proposal.md` (Layer 3 concept, self-hostable `verify-registry` deliverable). The calibration methodology this plan reuses — held-out corpus, transformation battery, measured rates published in `docs/CALIBRATION.md` before verdict influence — was established at W1/W2 and has corpora already on this machine (`D:\sandbox\corpus\div2k`, `D:\sandbox\corpus\calib`).

**G1 — PDQ in core, calibrated (no network, no log).** Scope: implement PDQ-256 in `crates/provenance-core` behind a default-off cargo feature `registry-pdq` (the layer stays gated; this is the hash alone). The algorithm from the public ThreatExchange spec: luminance from RGB, two-pass Jarosz box-filter downscale to 64×64, 16×16 DCT-II of the downscaled plane, output bit = coefficient > median, plus the spec's quality metric; ~300 lines, hand-rolled unless an audited crate proves better at implementation time (Decision Log entry then, either way). Known-answer tests against the reference implementation's published test vectors (the ThreatExchange repo ships photo → hash pairs; if licensing permits committing a few, do so with attribution, else generate KATs by running the reference locally, recipe checked in — the W1/W2 vector discipline). Calibration: extend `examples/calibrate.rs` (or a sibling) to compute pairwise PDQ distances over the existing corpora — same-image-across-transforms (the W2 battery: JPEG 90/70/50, resize 75/50, crop80, screenshot) versus different-image pairs from DIV2K — and publish, in a new PDQ section of `docs/CALIBRATION.md`, the distance distributions and the false-match rate at candidate thresholds (24, 31, 47, 63). Acceptance: `cargo test --workspace` green with and without the feature; KATs match the reference bit-for-bit; the calibration section exists with measured numbers and a chosen, justified threshold. Note the honest expectation going in: PDQ survives re-encode/resize well and crops poorly — crop robustness numbers get published, not excused.

**G2 — The log (shape per G0; maintainer deploys).** Common core regardless of shape, and identical formats so the pilot can migrate to the service: an entry encoding (canonical fixed-order binary of hash, registrant id, declared source type, RFC 3339 timestamp, Ed25519 signature), RFC 6962 leaf/node hashing (SHA-256 with the 0x00/0x01 domain-separation prefixes), checkpoint format (origin string, tree size, root hash, timestamp, Ed25519 signature — the Sigstore "signed note" shape), and the lookup nomination index (multi-index hashing: 256-bit PDQ split into sixteen 16-bit words; any exact word match nominates the entry — guarantees recall for distance ≤ 15 per missing-word bound at our thresholds, cheap to serve from static files as 65,536 bucket files per word position or a packed index). G2a additionally specifies the repo layout (`entries/NNNNNNNN.bin`, `checkpoints/latest.note`, `index/…`), the CI append-verification job (rebuilds the tree, checks consistency with the previous checkpoint, signs the new one), and the PR-based submission flow with per-registrant keys in a `registrants/` manifest. G2b wraps the same core in a single Rust binary (SQLite for entries, HTTP endpoints: `POST /entries`, `GET /lookup?word_i=…`, `GET /proof?leaf=…&size=…`, `GET /checkpoint`). Either way, seeding: our own corpus vectors registered under a project key, so G3 has something real to hit. Acceptance: a second, independent implementation of the verifier side (G3's client) accepts the deployed log's proofs — the log is not its own referee. Deployment itself is the maintainer's action.

**G3 — Layer 3 client, end to end (crypto sign-off on the proof verifier).** Scope: replace the stub in `layers/registry.rs` with the real layer behind feature `registry` (implies `registry-pdq`): a `RegistryTransport` trait injected at construction (sans-IO holds; CLI implements it over HTTP(S) or static-file fetch, tests implement it in-memory over a synthetic log), the flow compute-PDQ → nominate → verify inclusion proof against a pinned-or-fetched checkpoint → verify entry signature against the registrant manifest → Hamming distance ≤ calibrated threshold → `Indication { source: "matches an asset registered as AI-generated by <registrant> on <date> (verified inclusion proof, Hamming distance <d>)" }`; unreachable/malformed anything → `NotEvaluated { reason }`, never `NoSignal`, never a hit. The Merkle/signature verification code is signature-validation surface: branch + `lens-security-reviewer` packet + the maintainer's dated cryptography sign-off before merge, exactly like `layers/c2pa.rs`. CLI grows `--registry <url-or-dir>` (off by default); the extension's consent UI (per-lookup or per-site consent, with the manual's privacy statement) is its own maintainer approval and may trail the CLI. Acceptance: against the G2 log, a registered vector's stripped/re-encoded copy → Indicated with the full wording; an unregistered image → no registry finding; a log serving a bad proof or bad signature → NotEvaluated naming the failure; wording audited.

**G4 — Anchoring (optional; only on explicit request).** Publish each checkpoint hash to a public chain as an external witness on a ~daily cadence, verification remaining fully functional without it. No design work is spent here until asked; the standing decision (default off, never on a verdict path) already constrains it completely.

## Artifacts and Notes

Reference constructions, so a future reader needs no external search: RFC 6962 hashing — `leaf_hash = SHA256(0x00 || entry)`, `node_hash = SHA256(0x01 || left || right)`; inclusion proof = sibling hashes along the leaf-to-root path, verified by recomputation; consistency proof = the RFC 6962 subtree-consistency algorithm. PDQ operating points (from the public spec's guidance): distance ≤ 31 of 256 is the conventional match threshold; ≥ 70 is conventionally distinct. Multi-index nomination bound: 16 words of 16 bits — any entry within Hamming distance d < 16·k of a query shares at least one exact word when d ≤ 15 (pigeonhole over one word), and empirically nominates well beyond that; the G1 calibration measures actual nomination recall at our thresholds rather than trusting the bound.
