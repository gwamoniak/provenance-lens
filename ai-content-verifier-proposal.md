## 1. System Architecture

```
┌─────────────────────────────────────────────────────┐
│  Browser Extension (Provenance Lens)                │
│  content script → scans <img>/<video> → badge UI    │
└───────────────┬─────────────────────────────────────┘
                │ calls
┌───────────────▼─────────────────────────────────────┐
│  verify-core (Rust, compiled to WASM + native)      │
│                                                     │
│  Layer 1: C2PA manifest validation   (c2pa-rs)      │
│  Layer 2: Invisible watermark checks (detectors)    │
│  Layer 3: Registry lookup            (hash match)   │
│  Layer 4: Heuristic signals          (optional)     │
│                                                     │
│  → Verdict object with confidence tier + evidence   │
└───────────────┬─────────────────────────────────────┘
                │ optional network calls
┌───────────────▼─────────────────────────────────────┐
│  External services                                  │
│  • Trust list (C2PA conformance certs)              │
│  • SynthID / vendor detector APIs                   │
│  • Provenance registry (transparency log or chain)  │
└─────────────────────────────────────────────────────┘
```

### Detection pipeline (runs in order, cheapest first)

**Layer 1 — Cryptographic provenance (C2PA).**
Parse embedded Content Credentials with `c2pa-rs`. Validate the signature chain against a maintained trust list. This is the only layer that gives a *proof*, not a guess.
Output: signer identity, generator tool, edit history, timestamp.

**Layer 2 — Invisible watermark detection.**
If no manifest (the common case), probe for pixel-domain watermarks: SynthID detector API, Meta Stable Signature, `invisible-watermark` (Stable Diffusion default). These are vendor-specific — the library defines a `WatermarkDetector` trait so new detectors plug in without core changes.
Output: "watermark from vendor X detected" with detector confidence.

**Layer 3 — Registry lookup.**
Compute a perceptual hash (pHash/PDQ) locally and query provenance registries — C2PA's planned recovery services, Numbers Protocol, or the project's own transparency-log/blockchain-anchored registry. Catches images whose metadata was stripped on upload.
Output: "matches asset registered by X on date Y."

**Layer 4 — Heuristics (optional, off by default).**
ML classifier signals (frequency artifacts, GAN fingerprints). Always labeled as probabilistic, never shown as a verdict on its own. This layer is where overclaiming risk lives — treat it accordingly.

### Verdict model (what the user sees)

| Tier | Meaning | Badge |
|------|---------|-------|
| **Verified** | Valid C2PA manifest, trusted signer | Green: "AI-generated by X" or "Camera-captured, signed" |
| **Indicated** | Watermark or registry match, no manifest | Yellow: "Likely AI-generated (watermark: SynthID)" |
| **Inconclusive** | No signals found | Gray: "No provenance data — this does NOT mean it's authentic" |
| **Tampered** | Manifest present but signature invalid | Red: "Credentials broken — content may be modified" |

The gray tier's honest wording is a product decision as important as any code.

### Trust model

- **No self-appointed authority.** Trust list mirrors the C2PA conformance program; users/orgs can add or pin their own trust anchors.
- **Transparency log** (Sigstore/Rekor-style, optionally blockchain-anchored) for the registry, so registrations are append-only and publicly auditable. Chain anchoring is a checkpoint mechanism, not a dependency — verification works fully offline for Layers 1–2.
- **Privacy first:** images are never uploaded. Hashing and manifest parsing happen locally in WASM; only hashes leave the device, and only with user consent for Layers 2–3 network calls.

### Repos / deliverables

1. `verify-core` — Rust crate, native + WASM targets, C API for other ecosystems
2. `verify-wasm` — JS/TS bindings, npm package
3. `provenance-lens` — WebExtension (Chrome/Firefox/Edge, Manifest V3)
4. `verify-registry` — transparency-log service (self-hostable)
5. CLI tool — `verify image.png` for journalists/CI pipelines

> Status (2026-07-10): 1 → `crates/provenance-core` (scaffold; C API post-wedge). 2 → `crates/provenance-wasm` (scaffold; npm post-wedge). 3 → `extension/` (skeleton; functional at M3). 4 → not started, gated (M6; design captured in the `provenance-registry` skill). 5 → `crates/provenance-cli`, binary `lens` (scaffold). ## 2. Skills & Agents Proposition

Structure for building this with AI coding agents (e.g., Claude Code) plus a small human core. Each agent = a scoped subagent with its own skill file; each skill = a reusable instruction pack the agents load.

### Agents

| Agent | Scope | Key outputs |
|-------|-------|-------------|
| **Research Agent** | Track C2PA spec changes, watermarking papers, detector APIs | Weekly digest, gap analysis, threat landscape notes |
| **Rust Core Agent** | `verify-core` development: c2pa-rs integration, detector trait, verdict engine | Crate code, unit tests, benchmarks |
| **WASM/Bindings Agent** | wasm-bindgen builds, TS types, npm packaging, bundle-size budget | `verify-wasm` package, size/perf reports |
| **Extension Agent** | Content scripts, badge UI, options page, MV3 constraints, store submission | `provenance-lens` extension |
| **Security Review Agent** | Adversarial review: signature bypass, trust-list poisoning, malicious manifests, XSS in badge rendering | Threat model doc, review reports on every PR touching crypto |
| **Registry Agent** | Transparency log service, hash lookup API, anchoring job | `verify-registry` service + deployment recipes |
| **QA Agent** | Test corpus (signed/stripped/tampered/clean media), cross-browser e2e, regression suite | CI test harness, corpus repo |
| **Docs & Community Agent** | README, API docs, contributor guide, honest-limitations page | Documentation site, RFC templates |

### Skills (reusable instruction packs)

1. **c2pa-spec** — C2PA 2.x manifest structure, validation rules, trust list handling, known pitfalls in c2pa-rs
2. **watermark-detection** — detector trait contract, per-vendor integration notes (SynthID API, Stable Signature), calibration of confidence scores
3. **rust-quality** — project conventions: error handling (`thiserror`), no-panic policy in WASM paths, fuzzing targets for parsers
4. **wasm-packaging** — build pipeline, feature flags for size, JS interop patterns
5. **webextension-mv3** — Manifest V3 service-worker limits, CSP, per-store review requirements
6. **verdict-language** — the exact wording rules for each tier; forbids overclaiming ("no data ≠ authentic")
7. **security-checklist** — parser fuzzing, cert chain edge cases, downgrade attacks, supply-chain hygiene (pinned deps, signed releases)
8. **provenance-registry** — pHash/PDQ usage, transparency log append/verify flow, anchoring cadence

### Human roles still needed

- **Maintainer/architect** (you): decisions on trust model, verdict language, roadmap; reviews security-critical merges
- **Cryptography reviewer** (part-time/community): audits signature validation paths — agents draft, humans sign off here
- **Community manager** (later): triage, contributor onboarding, relations with C2PA and platform teams

### Build order

1. **Weeks 1–3:** `verify-core` Layer 1 only + CLI → already a useful tool
2. **Weeks 4–6:** WASM build + minimal extension showing Verified/Inconclusive badges
3. **Weeks 7–10:** Layer 2 detectors + verdict tiers + test corpus
4. **Then:** registry (Layer 3), heuristics behind a flag, store launches, community RFC process
