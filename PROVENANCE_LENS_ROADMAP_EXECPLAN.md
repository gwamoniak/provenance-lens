# Provenance Lens roadmap: review-driven hardening and the staged path to a real watermark layer

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It is maintained in accordance with the ExecPlan discipline in `PLANS.md` of the sibling repository `solid-broccoli` (same sandbox, `../solid-broccoli/PLANS.md` from this repo's parent; on this machine `D:\sandbox\projects\solid-broccoli\PLANS.md`).

This plan operationalizes an external technical review of provenance-lens 0.2.0 ("Provenance Lens — Proposed Changes & Roadmap", received 2026-07-31; its full substance is restated in Context and Orientation below, so this plan does not depend on that file). It is the third plan in the repo: `PROVENANCE_LENS_EXECPLAN.md` (the wedge, M0–M4 shipped; M5–M7 gated) and `PROVENANCE_LENS_UPGRADES_EXECPLAN.md` (U1–U7, fully executed) remain authoritative for their scopes. Where this plan proposes revising a gate defined in the wedge plan, that revision takes effect only when the maintainer approves it and the wedge plan's Decision Log records it.

## Purpose / Big Picture

After this plan, a reader of the README can no longer infer a capability the tool does not have (SynthID is not third-party-detectable and the docs will say so); a user staring at a "Tampered" verdict can tell a broken signature apart from a signature whose signer simply is not on our — possibly stale — trust list; the docs position the tool inside the EU AI Act Article 50 ecosystem that takes effect 2026-08-02; and Layer 2 (watermark detection) has a concrete, honesty-preserving path from "gated stub" to two real detectors with measured false-positive rates — followed by a recorded strategic decision to invest in the registry (Layer 3) before heuristics (Layer 4). Nothing in this plan relaxes the founding rule (**no provenance data ≠ authentic**) or the sign-off rule (signature-validation changes merge only with the maintainer's recorded cryptography sign-off).

- Observation: IMATAG's open detector (`imatag/stable-signature-bzh-detector-resnet18` on Hugging Face, stated ~1/1000 false positives) detects ONLY images produced by IMATAG's own watermarked SDXL-VAE variants ("bzh"), not Stable Signature deployments in general.   Evidence: the model card states it "works on this watermark only and cannot be used to decode other watermarks".
- Observation: GitHub auto-disables scheduled workflows after 60 days without repository activity, and a disabled monthly trust-list refresh fails silently — exactly the staleness path A3 warns about. Alerting on failure cannot catch "never ran"; R2 therefore also puts the trust-list date into the product's own evidence output, which degrades visibly instead of silently.
  Evidence: GitHub Actions documented behavior for `schedule` triggers on inactive repositories.
- Observation: The reference "dwtDct" method applies NO discrete cosine transform anywhere in its embed/decode path — the name is a misnomer in the library; the scheme is Haar-DWT + max-coefficient quantization-index-modulation on 4×4 LL blocks. Only the separate `infer_dct_svd`/`diffuse_dct_svd` variant (method 'dwtDctSvd') touches `cv2.dct`. A from-memory reimplementation would almost certainly have inserted a DCT and matched nothing.
  Evidence: fetched `imwatermark/maxDct.py` verbatim (2026-07-31): `decode_frame` passes the raw LL block straight to `infer_dct_matrix`, which does argmax + modulo only.
- Observation: Smooth synthetic base images are PATHOLOGICAL for this watermark: embedding a 0-bit *shrinks* the block's max LL coefficient by up to 27 (scale·0.75), and on low-contrast blocks the decode-time argmax then lands on an unmodified neighbour — the first generated vector failed to decode through the REFERENCE decoder itself (every block read as a 1). Blurred seeded noise (photo-like texture) fixes it; 768×768 is needed for the 136-bit payload's per-slot vote count; and per-vector seeds had to be scanned because most seeds leave at least one bit-slot vote within 0.002 of the decision threshold, where the ±1 U-plane rounding differences between OpenCV and any reimplementation would make the known-answer test flaky. The generator now self-verifies (reference-decodes the written file) and enforces a ≥ 0.03 worst-slot margin.
  Evidence: seed scan 2026-07-31 — at 768², SDV1 decodes fully for only 2 of 13 seeds (margins 0.042 / 0.013); the shipped vectors use seed 2 (SDXL, margin 0.061) and seed 10 (SDV1, margin 0.042).
- Observation: The Rust decoder's intermediates match the reference numerically before any tuning: the analog BT.601 U-plane formula differs from OpenCV's fixed-point `cvtColor` by at most 1 (mean |diff| ≈ 1e-5) and the quad-sum/2 Haar LL matches `pywt.dwt2` to 1e-13 — the divergence that failed the first KAT was entirely the vector's, not the decoder's.
  Evidence: side-by-side dump on the first vector (debug session 2026-07-31).
- Observation: transformers 5's `AutoImageProcessor` silently mangles the bzh model's preprocessing (it maps to a fast torchvision processor): the vendor's watermarked example scored +7.8 ("not watermarked") instead of −11.4. The vendor's own `BlipImageProcessor` — and plain manual bicubic-512/rescale/normalize, which matches it to 1e-6 — give the correct answer. A wrapper upgrade would have shipped a detector that detects nothing, and only the vendor-example KAT caught it.
  Evidence: diagnostic session 2026-08-01; correct reference logits −11.3869 (watermarked) / +27.1844 (clean).
- Observation: Calibration made the DWT scheme's fragility a number instead of folklore — 45% TPR on pristine reference embeds of real photographs, 0% after ANY single transform (even JPEG q90) — while the same tables show it never invents a hit (0 FP across 800 transformed clean variants + 2,861 flat clean images). The exact-payload rule trades recall for a false-positive rate indistinguishable from zero, which is precisely the trade this project wants.
  Evidence: docs/CALIBRATION.md tables, 2026-08-01.
- Observation: The bzh classifier detects CROPPED watermarked images better than untouched ones (crop80 85% vs orig 51%). Consistent explanation: the model consumes 512²; a 768² input is downscaled 1.5×, attenuating the high-frequency watermark, while an 80% crop is only downscaled 1.2× — proximity to the model's native scale matters more than pixel loss. Also: VAE-roundtripped photographs are a harder distribution than the SDXL generations the vendor targets, so ~51% orig TPR is a floor, not the vendor's number.
  Evidence: docs/CALIBRATION.md bzh table, 2026-08-01.

## Outcomes & Retrospective

- (2026-08-01) **W2 closed — Layer 2 now has two real detectors and a published conscience.** Outcome: the IMATAG bzh classifier runs in pure Rust (tract) off a user-supplied ONNX export of MIT weights, wired through the same trait as the DWT decoder; and `docs/CALIBRATION.md` publishes what both detectors actually do under the transformation battery, measured by the exact production probes on a held-out corpus. Remaining in this plan: W3 stays vendor-gated (`lens-research` watches the Content Detection API), W4 registry design on the maintainer's word.

## Context and Orientation

The repository (`D:\sandbox\projects\provenance-lens`, public at https://github.com/gwamoniak/provenance-lens) is one Rust workspace: `crates/provenance-core` (sans-IO verification pipeline), `crates/provenance-cli` (the `lens` binary, owns file I/O), `crates/provenance-wasm` (thin WASM wrapper), and `extension/` (MV3 browser extension for Chrome and Firefox ≥128, plain JS, consumes the wasm-pack output). An asset flows through four layers ordered by evidentiary strength: Layer 1 C2PA cryptographic proof (real, shipped), Layer 2 watermark (honest stub, gated milestone M5), Layer 3 registry lookup (honest stub, gated M6), Layer 4 heuristics (honest stub, optional M7). Only Layer 1 may return `Proof`; every other layer's ceiling is `Indication`. Verdicts combine as Tampered > Verified > Indicated > Inconclusive, and the four verdict phrases are canonical: pinned character-identical across `README.md`, `extension/popup/popup.html`, `.claude/skills/verdict-language/SKILL.md`, `crates/provenance-wasm/README.md`, and `docs/MANUAL.md` by `crates/provenance-core/tests/wording_sync.rs` — any new user-facing string in this plan goes through the `verdict-language` skill and, if a location gains a canonical phrase, through that test.

Standing rules that bind every milestone here: the **sign-off rule** (any change to `crates/provenance-core/src/layers/c2pa.rs`, trust-list handling, or cert policy lands on a branch and merges only with the maintainer's dated cryptography sign-off in the wedge plan's Decision Log; agents never merge those); the **bare-machine rule** (a fresh clone with no network and no models must build and pass 100% of tests); the **privacy rule** (image bytes never leave the device; Layers 2–3 may eventually send perceptual hashes only, with explicit consent); and **new dependencies require a Decision Log entry**.

The external review being operationalized said, in substance: (A1) the README pipeline diagram lists "Watermark — vendor detectors (SynthID, …)" and readers will infer SynthID detectability, which no third party has — add a caveat; (A2) keep the c2pa bump automation and CI fuzz active until the fixed upstream release lands (already true, see Surprises); (A3) a stale trust list turns fresh legitimate credentials into Tampered — the worst false accusation this product can make — so monitor the refresh workflow for failure and add an evidence sub-state "valid signature, signer not on trust list (list dated YYYY-MM-DD)"; (A4) EU AI Act Article 50's transparency obligations (in force 2026-08-02) mandate marking by generators, not verifiers — a positioning tailwind worth a docs section framing Provenance Lens as the independent verification side of that ecosystem; (B1) implement the `WatermarkDetector` trait for real with the Stable Diffusion `invisible-watermark` DWT-DCT decoder (fully open, locally runnable, spec-known) as the forcing function for the hard design decisions — image-decode dependency, WASM-vs-native, where the bare-machine rule bends; (B2) add IMATAG's open Stable Signature ResNet-18 detector behind the same trait, plus a labeled calibration corpus (watermarked vs clean, each run through JPEG re-encode at several qualities, resize, crop, screenshot) with published per-detector per-transformation TPR/FPR before Layer 2 may influence verdicts; (B3) never claim local SynthID detection — only an opt-in consent-gated online vendor connector when access exists, and/or explicitly-labeled metadata-proxy inference ("manifest signed by a known SynthID-embedding issuer → SynthID likely present", which goes silent when the manifest is stripped); (B4) pull registry work forward ahead of heuristics because the perceptual-hash registry is what survives metadata stripping and watermark removal.

Terms used below: **DWT-DCT** — discrete wavelet transform + discrete cosine transform, the pure-signal-processing embedding used by the open `invisible-watermark` library that Stable Diffusion's reference pipelines apply to their outputs (a fixed payload embedded in the image's frequency domain; decoding is deterministic math, no ML model). **ONNX** — an interchange format for neural-network models; running one in Rust requires an inference runtime crate (`ort` wraps onnxruntime, native-only in practice; `tract` is pure Rust). **FPR/TPR** — false/true positive rate. **Transparency log** — an append-only Merkle-tree log (as in Certificate Transparency) whose inclusion proofs let anyone verify an entry without trusting the operator.
